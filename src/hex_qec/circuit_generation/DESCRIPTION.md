# `circuit_generation`

This package contains the current code-data loader, code-block allocator, and
Stim circuit builders.  It is a procedural module; there are no circuit or
code classes.

## Code-data convention

`get_parity_check_matrices(code, distance)` searches
`parity_check_matrices/<code>/` for four Matrix Market files ending in
`hx.mtx`, `hz.mtx`, `lx.mtx`, and `lz.mtx`.  It returns

```text
(x_pcm, z_pcm, x_logical, z_logical)
```

The checked-in files load through `scipy.io.mmread` as sparse COO matrices
(integer-valued in the current data).  Their axis convention is:

```text
x_pcm, z_pcm:     (number of stabilizer checks, number of data qubits)
x_logical, z_logical:
                  (number of logical operators, number of data qubits)
```

Rows are operators and columns are physical data-qubit positions.  The code
assumes `x_pcm.shape[1] == z_pcm.shape[1]`.  The tuple is passed unchanged
through the rest of Hex; it is not converted to a dense ndarray by the
loader.

The package-level `__all__` currently lists only
`get_parity_check_matrices` and `stabilizer_measurement_circuit`, although
`__init__.py` imports additional helpers by name.

## Layout helpers

`generate_blocks(number_of_blocks, block_template)` copies a template block
and offsets every qubit index by

```text
len(data_qubits) + len(x_ancillas) + len(z_ancillas)
```

Each returned block is a dictionary with three list-valued entries:
`data_qubits`, `x_ancillas`, and `z_ancillas`.  The template generated by
`create_stabilizers_and_block_template` allocates data qubits first, then X
ancillas, then Z ancillas.  The corresponding counts are
`n`, `m_x`, and `m_z`, where `n = x_pcm.shape[1]`, `m_x = x_pcm.shape[0]`,
and `m_z = z_pcm.shape[0]`.

`sparse_binary_array_to_paulistrings(sparse_binary_array, pauli)` converts
each row into a length-`n` `stim.PauliString`; nonzero row entries become the
requested Pauli.  `create_stabilizers_and_block_template(...)` uses these
strings to construct Tableau circuits for logical `|0>` and logical `|+>`
preparation and returns:

```text
(block_template, (x_stabilizers, z_stabilizers, logical_X, logical_Z),
 logical_0_prep_template, logical_plus_prep_template)
```

Redundant check rows are retained (`allow_redundant=True`).

## Elementary circuit builders

The following helpers append operations to a supplied `stim.Circuit`:

- `qubit_initialisation(circuit, pauli, block, prob)` prepares data qubits in
  `|0>` (`R` followed by `X_ERROR(prob)`) or `|+>` (`RX` followed by
  `Z_ERROR(prob)`).
- `qubit_measurement(circuit, pauli, block, prob)` applies the corresponding
  final measurement error and uses `M` for Z-basis or `MX` for X-basis
  measurement.
- `measure_X_stabilizers` and `measure_Z_stabilizers` prepare ancillas,
  apply the stabilizer interaction (`CX` for X checks and `CZ` for Z checks),
  insert `DEPOLARIZE2(prob)` after each interaction, and measure/reset the
  ancillas with `MR`.
- The `_surface_code` variants use special interaction ordering for weight-2
  and weight-4 checks.  Their diagnostic messages are controlled by the
  parent builder's `debug` argument and are silent in normal simulation.  The
  normal protocol path leaves `surface_code=False`.
- `transversal_cnot(circuit, first_block, second_block, prob)` appends one
  physical CNOT per pair of data qubits and one multi-target `DEPOLARIZE2`
  instruction over the pairs.
- `ideal_preparation_circuit(circuit, block, template)` remaps the template's
  qubit indices to the block's data-qubit list by rewriting the Stim text.

The `prob` argument is reused for initialization, ancilla preparation and
readout faults, two-qubit depolarization, and data measurement faults in the
current model.  The builders do not define a separate noise-model object.

## Repeated syndrome-extraction circuits

`stabilizer_measurement_circuit(...)` prepares one noisy encoded state, runs
`syndrome_repetitions` rounds, and optionally appends final data measurement,
terminal detectors, and an observable.  Initial detectors include only the
stabilizer type deterministic for the requested `pauli`; later rounds compare
the current X/Z ancilla results with the immediately preceding results.

`stabilizer_measurement_circuit_both_detectors(...)` has the same preparation
and repeated-round structure but emits both X and Z detector families and
does not append final data measurements in the default configuration.  For a
surface-code distance-3 example with four X and four Z checks, three rounds
produce 24 measurements and 20 detectors.  In general, each round produces
`m_x + m_z` measurements; the detector count is

```text
(m_x or m_z) + (syndrome_repetitions - 1) * (m_x + m_z)
```

for the single-detector builder, and

```text
(m_x or m_z) + (syndrome_repetitions - 1) * (m_x + m_z)
```

for the both-detector builder as well, with the first term selecting the
prepared state's deterministic family and subsequent rounds containing both
families.  `generate_state_prep_modules` relies on this exact ordering.

`noiseless_unitary_state_prep(parity_check_tuple, pauli, eigenvalue)` returns
the Tableau-derived encoded-state preparation circuit.  `eigenvalue == 1`
adds a physical X for a Z-basis state or physical Z for an X-basis state on
all data qubits; other values do not trigger that addition.

## Dependencies and call flow

The module depends on Stim, NumPy types, SciPy's Matrix Market reader, and the
Python standard library.  A normal protocol call flows as:

```text
get_parity_check_matrices
  -> create_stabilizers_and_block_template
  -> generate_blocks
  -> stabilizer_measurement_circuit_both_detectors
  -> modularisation/module_generation.py
```

The generated circuits are consumed by the modularisation layer, which adds
DEM decoding and correction propagation.

## Current limitations

- The implementation assumes CSS-style X/Z check matrices and does not
  validate commutation, rank, or logical-operator independence.
- File lookup uses the first glob match and raises the underlying indexing
  error if a requested code or distance is absent.
- Pauli, distance, and repetition arguments have limited validation; invalid
  Pauli values can silently omit operations in some helpers.
- Circuit construction is repeated for each requested configuration and is
  not a stateful or adaptive execution mechanism.  Repeated rounds are
  statically described before sampling.
- The surface-code-specific path is selected only when a protocol or builder
  is explicitly called with `surface_code=True`; the default remains
  `False` for backward compatibility.
